# 提示词：从原始数据提炼律师工作日志规则

> 用法：把本提示词 + `3_raw_recorder` 采集的 JSONL 数据（跑 3-7 天）一起交给 AI，
> 让它输出插件2 直接加载的规则集 `Rules.json`。

---

## 你的角色

你是一位「律师行业工作流 + 行为数据分析」双料专家。既懂律师怎么工作（文书、检索、会见、出庭、案卷管理、计时收费的 billable hour 概念），也懂怎么从原始传感器数据里提炼可执行规则。你的产出会被一个守护程序直接加载，用于把「正在干什么」自动归类成「工作日志条目」。

## 背景：数据从哪来

数据来自 macOS 上的原始采集器，每 5 秒一行 JSONL，字段含义：

| 字段 | 含义 | 说明 |
|------|------|------|
| `ts` | 时间戳 | 格式 yyyy-MM-dd HH:mm:ss |
| `app` / `bundle_id` | 前台 App | |
| `pid` | 进程号 | |
| `window_title` | 窗口标题 | 可能为空（无屏幕录制权限） |
| `dir` | 从标题提取的路径片段 | 可能是 `cases/张三诉李四/答辩状.md` 这类 |
| `idle_sec` / `mouse_moved_sec` | 键鼠空闲秒数 | 越大越可能在离开/阅读 |
| `charging` / `on_battery` / `battery_pct` | 电源 | |
| `iface` / `ip` / `gateway` | 网络 | en0=Wi-Fi，en2=LTE |
| `ssid` | 无线网络名 | 可能为空 |
| `displays` / `display_sleep` | 显示器 | display_sleep=true 表示屏幕已熄 |
| `cpu` / `mem_free_gb` | 负载 | |
| `bt` | 蓝牙设备 | 可能为空 |
| `event` | 事件行 | "start"/"sleep"/"wake"/"stop" |

## 你的任务

基于**真实数据**（不许臆造数据里不存在的模式），完成四件事：

### 1. 工作片段切分规则（segment）

定义：什么时候算一段"连续工作"，什么时候切下一段。请给出：

- 空闲多少秒算「离开/打断」？（默认值 + 依据数据中观察到的实际分布）
- 睡眠/唤醒事件如何作为硬边界？
- 最短片段时长（过短的丢弃，比如 <3 分钟）
- 时间上相邻、同一案件的两段是否合并？

### 2. 活动类型分类规则（activity_types）

把工作片段归类为类型。律师行业典型类型，请按你的判断给出一组（可增减）：

- `drafting` 文书写作（起诉状/答辩状/合同/意见书）
- `research` 案例/法条检索
- `client_comms` 与当事人沟通（微信/邮件/电话）
- `meeting` 会议/会见
- `court` 出庭（如果数据里有迹象）
- `admin` 行政事务（表格/报销/日程）
- `other_work` 其他工作
- `break` 休息

每个类型的判定依据，**必须基于 App/窗口标题/输入模式**给出具体规则，例如：
- App ∈ {Pages, Word, Typora} 且标题含 `.docx`/`答辩` → drafting
- App ∈ {Safari, Chrome} 且标题含 `裁判文书网|北大法宝|威科先行|无讼|alpha` → research
- 长空闲后键盘恢复 + 通讯 App → client_comms

### 3. 案件归属提取规则（case_extraction）

这是最关键的。律师的文件目录/窗口标题往往包含当事人名或公司名。请：

- 观察数据中 `dir` 和 `window_title` 的实际形态，归纳路径结构规律（如 `案卷/张三诉李四/`、`合同/XX公司-框架协议/`）
- 给出提取「当事人/案件名」的规则：关键词、分隔符、姓氏+「诉」模式、公司后缀（有限公司/股份/事务所）
- 给出「公司名常见后缀表」和「法律文书常见文件名表」（起诉状、答辩状、上诉状、代理词、合同、尽调报告……），供提取用
- **判断不出来怎么办**：明确给出「需要询问」的触发条件（哪些信号表明在干活但无法归属案件）

### 4. 职业共性与个性

分两部分输出：

- **共性**（全国律师通用，不依赖这份数据就能写）：作息节律、文书/检索/沟通的比例结构、收费行业（billable hour）关心的字段
- **个性**（只来自这份数据）：这位律师的上下班时间、常用软件组合、常用目录结构、案件命名习惯、加班规律

## 输出格式

只输出一个 JSON 对象（`Rules.json`），结构如下，字段不许多不许少：

```json
{
  "schema_version": 1,
  "segment": {
    "idle_cutoff_sec": 600,
    "min_segment_min": 3,
    "merge_gap_min": 10,
    "note": "理由一句话"
  },
  "activity_types": [
    {
      "type": "drafting",
      "label_zh": "文书写作",
      "rules": ["app in [...] and title matches /.../", "..."],
      "note": "判定依据描述"
    }
  ],
  "case_extraction": {
    "path_patterns": ["正则/或描述"],
    "person_suffixes": ["诉", "vs", "v."],
    "company_suffixes": ["有限公司", "股份", "事务所"],
    "doc_keywords": ["起诉状", "答辩状", "代理词", "合同", "尽调报告"],
    "ask_when": "无法归属案件时的触发描述（守护程序据此弹询问）"
  },
  "common": ["共性1", "共性2"],
  "personal": ["个性1", "个性2"],
  "confidence": {"high": ["哪些结论可信"], "low": ["哪些证据不足"]}
}
```

## 硬约束

1. **每个规则都要能在数据里找到依据**，写不出来的标 `need_data`，不许编
2. `confidence.low` 必须诚实列出——数据只有 3 天、没有周末、没拍到过出庭，就明说
3. 正则规则要写进 `rules` 字段（JSON 字符串，程序直接执行），描述写 `note`，不要混在一起
4. 输出纯 JSON，不要解释性文字
